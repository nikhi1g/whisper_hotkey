# whisper_hotkey 3.5.5: Readable Settings

Adding five engines, six models, three processing modes and two decoding
profiles was each defensible on its own. Together they produced a window a
normal person could not read.

## What was actually wrong

- Two adjacent rows were both labelled `Fast | Accurate` and meant different
  things: one was the preset, one was the Parakeet checkpoint.
- The Engine row offered "Metal", "Core ML Encoder" and "WhisperKit" — three
  words that describe how the code runs, not what the user gets.
- A row called **Recognition** sat inside a section called **RECOGNITION**.
- Six chips along the bottom repeated the hotkey, mode, model, limit, theme and
  login state, all of which were already visible in the rows above.
- Whenever the configuration matched neither preset, the preset control showed
  nothing selected. An unselected segmented control reads as broken, not as a
  state.

## What changed

**Engine and Model became one list.** Ten named configurations grouped by
family, with the ones needing no download first:

| Parakeet | Whisper | Cohere |
| --- | --- | --- |
| Accurate — recommended | Turbo · Base | Transcribe — slowest |
| Fast | Turbo/Base (Core ML encoder) | |
| Unified — most accurate | Turbo/Base (WhisperKit) | |

The old two-row arrangement described a matrix whose cells were not all valid:
decoding applies to two engines of five, the model row meant a different thing
per engine, and several pairings could not run. A list of real choices has no
invalid cells. `RecognitionChoice` is a presentation type over the existing
`recognitionEngine`, `dictationModel` and `parakeetModel` preferences, so
nothing is migrated, and a test asserts every pairing the old matrix could
reach is still offered.

**Custom is a real segment** — permanently disabled, selected when the
configuration matches neither preset, so the control reports a state instead of
appearing empty.

**Quality**, not Recognition. **The footer chips are gone.** **Keeping the last
dictation is one control**, not a label and a checkbox saying the same thing.

Collapsed, the Recognition section is two rows rather than four.

## Processing defaults to Model Ready

In both presets and on first run. Model Ready decodes the whole recording, so
it is exactly as accurate as After Recording, and the model is already resident
so the load latency disappears. Decode While Speaking is the mode that trades
accuracy for perceived speed by decoding chunks without cross-chunk context —
a reasonable choice, but the wrong one to make on a user's behalf.

All three modes remain selectable under Advanced Options.

## Deliberately not in this release

The guided first-run window. Today a new user meets three surfaces before
dictating once — an install prompt, the Setup window, and Settings opening
itself — and nothing in the app ever confirms that dictation works. That flow
is designed and written up in `docs/design/welcome-window.md`, including the
finding that the "try it" step needs no new dictation plumbing because
delivering a transcript into the app's own window is already a shipped path.
It is the larger half of this problem and it is still open.

## Compatibility

No preference is migrated or rewritten. Every engine, model, decoding profile
and processing mode remains selectable.
