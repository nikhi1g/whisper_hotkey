# whisper_hotkey 4.3.1

Candidate: 2026-09-12. Not published.

## Immediate provisional work

- Start recorder admission on the physical key edge, independently of gesture acceptance, models, Accessibility, and UI placement.
- Use AVAudioSinkNode render quanta for Model Ready and Decode After Speaking, avoiding the input tap's additional buffer-coalescing delay.
- Retain one owned native-buffer copy in the existing bounded writer FIFO; preserve its onset samples and reject overflow visibly.
- Run provisional badge waveform/timer updates before Hold dwell or Toggle release acceptance.
- Adopt capture asynchronously and preserve the existing badge history and elapsed time across acceptance.
- Cancel rejected provisional tokens, their private audio, and their presentation/diagnostic tasks without recognition or insertion.

## Full-context completion

- Prepare Decode After Speaking only after sealing the complete WAV. Model Ready may warm after recorder admission but never decodes partial audio.
- Capture the destination at finish input and retain continued speech until cadence-aware silence or the bounded rational maximum wait.
- Keep cancellation, recording limits, stale-token guards, exactly-once finalization, and private-audio cleanup authoritative.
- Leave Decode While Speaking and Pause Mode's tap, segmentation, decoding, reconciliation, prompts, and completion behavior unchanged.

## AirPods playback coexistence

- When Automatic would use a Bluetooth headset for both default input and
  output, route only whisper_hotkey capture through an available built-in
  microphone.
- Leave the macOS input default, output default, and current playback untouched.
- Preserve USB and other independent default inputs.
- Honor every explicit manual microphone choice without substitution.
- Keep macOS-generated default aggregates internally resolvable while hiding
  their implementation names from the microphone menu.

## Verification contract

- Run the focused capture, hotkey, mode-matrix, and coordinator tests, the full Swift suite, and bootstrap/release-tooling tests.
- Verify native render-buffer copying survives Core Audio reusing the original memory before the writer attaches.
- Measure queue admission, engine startup, first non-empty buffer, first committed sample, and badge visibility independently in the installed app.
- Exercise provisional rejection, accepted capture, finish, and cancellation with the selected microphone; check idle resources and private-audio deletion.
- Verify the installed executable path, bundle version, deep signature, and built/installed app and controller hashes.
- Report hardware startup latency honestly. No software queue can recover sound captured before the microphone hardware begins supplying samples, and no microphone remains active at idle.

## Local verification results

- Full Swift suite: 402 tests, 3 skipped, 0 failures. Bootstrap/release tooling: 16 tests passed.
- Native AppKit badge smoke: the existing badge rendered its waveform, `0:01` timer, Stop, and Send at 203 × 42 points. OS window capture was unavailable, so this was an in-process native rendering check.
- Installed Bluetooth-input measurements: a warm start admitted work in 0.127 ms, showed the badge in 1.558 ms, started the engine in 14.956 ms, received its first buffer in 25.159 ms, and committed it in 25.306 ms. The observed prior tap path first committed at about 123 ms; these are individual measurements, not a hardware-independent benchmark.
- A cold start still took 256.845 ms to commit the first hardware sample, despite 0.109 ms admission and 7.794 ms badge visibility. This remaining microphone startup interval is not recoverable without keeping capture active at idle, which this release does not do.
- A 50 ms rejected Hold retained no accepted dictation session. Accepted capture and cancellation returned to idle. These probes do not establish spoken-transcript accuracy or guarantee preservation of sound produced before hardware capture starts.
- The installed app passed deep strict signature verification and matched the built app/controller hashes. The embedded login launcher was verified as 4.3.1 after correcting a stale incremental 4.2.7 product.
- The installed helper reached its argument-validation response with the build-time library directory temporarily unavailable. The app, controller, launcher, helper, and six bundled libraries all target macOS 14.0.
- The local candidate is Apple Development signed. The production build passed its deployment-target gate but stopped because this machine has no Developer ID Application signing identity. No notarization or publication was performed.

## Distribution

The helper and its libraries use bundle-relative runtime search paths. Local
verification must run the installed helper with the build-time dependency
directory unavailable, so a developer machine cannot hide a missing bundled
library.
The build also checks both embedded launcher version fields and relinks a stale
SwiftPM product before packaging; changing the excluded linker-input plist alone
does not invalidate SwiftPM's cached executable.

Production publication requires Developer ID Application signing, hardened runtime, secure timestamps, notarization, stapling, and Gatekeeper assessment. This local candidate does not authorize publication or substitute Apple Development signing for those gates.
