# Version 4.3.0 capture latency and dynamic tail plan

Status: review only. Do not implement until approved.

## 1. Instant recording start

**Problem:** Speech can begin immediately after Right Option. Model setup must never delay microphone capture or compete with the real-time audio path.

**Decision:** Treat the physical hotkey edge as two independent branches:

1. Enqueue token-scoped microphone capture immediately.
2. Start model preparation concurrently on its existing actor.

The model may finish before or after speech. Finalization waits for model readiness, but recording never does. Preserve the current private ordered audio queue and exactly-once session token.

“Sub-millisecond startup” will mean less than 1 ms from the event callback to capture work being enqueued. Hardware first-buffer latency cannot honestly be guaranteed below 1 ms because Core Audio and the selected device control it. The user-facing invariant is stronger and measurable: no onset samples are lost, even when speech starts immediately. Human reaction time is roughly 150 to 250 ms, so the software dispatch target is comfortably below perception while first-buffer latency is reported separately.

## 2. Dynamic trailing buffer

**Problem:** Pressing Return at the exact end of speech can finalize before the last phoneme reaches the audio callback. The current rule grants a fixed 240 ms only when confirmed speech has less than 180 ms trailing silence, so uncertain VAD state can skip protection.

**Decision:** Capture the release-time destination and consume Return immediately, but keep audio open until either:

- observed silence reaches an adaptive target derived from recent pause cadence; or
- a strict maximum post-roll expires.

Start with a 180 ms minimum, use recent pause evidence to grow toward 450 ms, and cap total post-roll at 500 ms. Recent confirmed speech receives the minimum even if VAD is temporarily uncertain. No-speech sessions and already-silent sessions finalize immediately. Model preparation continues concurrently during post-roll.

## Planned agent orchestration after approval

Run three independent agents first:

1. **Capture path:** instrument hotkey-to-enqueue and enqueue-to-first-buffer timing; enforce token ownership and no model dependency.
2. **Tail policy:** implement the pure adaptive post-roll policy and boundary tests for speech, uncertain VAD, silence, cadence, and cap.
3. **Behavior audit:** map Hold, Toggle, Pause, Return, badge Stop, cancellation, maximum duration, and privacy cleanup against the new contracts.

After those complete, run one integration agent to wire the approved contracts into application orchestration and update focused tests. The main orchestrator then runs the full suite, builds and installs the signed app, verifies the actual menu and TextEdit completion path, measures capture timing, and commits only a green tree.
