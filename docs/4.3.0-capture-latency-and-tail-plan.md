# Version 4.3.0 recorder and transcriber plan

Status: approved and implemented on main; pending repository and signed-runtime verification.

## Scope

This change applies only to **Model Ready** and **Decode After Speaking**. Do not change **Decode While Speaking**. Its segmentation, concurrent decoding, reconciliation, and prompt behavior are a separate, more complex system.

## Mental model: three independent participants

1. **User:** presses Right Option, speaks, then releases it or presses Return to finish.
2. **Recorder:** starts from the physical input edge and does only bounded audio capture work. It must not wait for a model, Accessibility, badge placement, formatting, or transcription.
3. **Transcriber:** receives one sealed, complete recording only after the recorder finishes. It never decides when recording ends.

## Beginning of speech

The hotkey callback immediately enqueues a token-scoped recorder start. Target less than 1 ms from callback to queue admission. Actual first-buffer latency is reported separately because Core Audio and the selected hardware control it.

Keep the recorder close to existing AVAudioEngine and Audio Unit primitives. Avoid a custom driver or audio stack. The callback copies or references only the samples required by the existing bounded queue; conversion and file writes remain off the real-time callback. Model work cannot run on the capture queue.

For **Model Ready**, model preparation begins concurrently after capture has been admitted, but decoding waits for the sealed recording. For **Decode After Speaking**, model preparation begins only after sealing. Both modes use the same complete recording and must preserve its first sample.

## End of speech

The current fixed conditional post-roll can miss a final phoneme when the finish input arrives before the audio callback or while VAD is uncertain.

Utterance duration alone is not a reliable stopping signal. A long sentence does not inherently need more silence than a short sentence. Use observed audio as the primary rule:

1. On release or Return, capture the destination immediately and enter **finishing capture**.
2. Continue recording until confirmed trailing silence reaches a cadence-aware target.
3. If the user keeps speaking after the finish input, reset trailing silence and retain that speech.
4. Seal only after the silence target, subject to a strict maximum wait.

Use a rational saturation function only for the maximum wait, not for the normal stop decision:

`maximumWait(d) = 0.25 + 0.75 * d / (d + 10)` seconds

Here `d` is confirmed speaking duration. The cap begins at 250 ms, is about 750 ms after 20 seconds, about 894 ms after one minute, and approaches but never exceeds one second. This is monotonic, bounded, and cheaper and easier to test than fitting an exponential curve.

The normal silence target remains cadence-aware within conservative bounds. No-speech and already-silent sessions finalize immediately. Cancellation remains immediate. The recording limit remains authoritative. Return is consumed immediately, but insertion waits for final transcription.

## Required invariants

- No onset or final spoken samples are lost.
- Exactly one sealed recording reaches the transcriber.
- Model Ready may warm concurrently but never decodes partial audio.
- Decode After Speaking performs no model work before sealing.
- Decode While Speaking is behaviorally and structurally untouched.
- Temporary audio is deleted on success, cancellation, failure, and termination.
- No new polling loop, idle helper, transcript log, or unbounded buffer.

## Planned orchestration after approval

Parallel first wave:

1. **Recorder agent:** hotkey-to-capture admission, real-time callback constraints, queue ownership, timing evidence.
2. **Tail-policy agent:** pure silence and rational-cap policy, cadence interaction, boundary tests.
3. **Mode-audit agent:** prove Model Ready, Decode After Speaking, and excluded Decode While Speaking boundaries across Hold, Toggle, Return, badge Stop, cancellation, and recording limit.

Dependent second wave:

4. **Integration agent:** wire only the approved contracts into application orchestration and update focused behavioral tests.

The main orchestrator then runs the full suite, builds and installs the signed app, verifies immediate speech and final-word retention in TextEdit, measures callback-to-admission and first-buffer latency separately, and commits only a green tree.
